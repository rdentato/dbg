# dbg Manual

`dbg` is a small, header-only C debugging and testing helper. It lets you keep diagnostic, test, trace, timing, and allocation-checking instrumentation in normal source files while controlling that instrumentation with compile-time switches.

The library is implemented in `src/dbg.h`. There is no library to link: include the header and compile with the preprocessor switches you need.

The enabled `dbg` macros emit structured log records instead of analyzing or formatting those records inside the application. The `dbglog` tool must read the raw log to perform formatting, trace validation, memory validation, and report generation. This separation minimizes the runtime impact of the macros on the instrumented program.

## Quick Start

Create `example.c`:

```c
#include "dbg.h"

int add(int a, int b) {
  dbginf("add(%d, %d)", a, b);
  return a + b;
}

int main(void) {
  dbgtst("basic arithmetic") {
    dbgchk(add(1, 1) == 2);
    dbgchk(add(2, 2) == 5, "expected 4, got %d", add(2, 2));
  }

  return 0;
}
```

Compile with test-level debugging enabled:

```sh
cc -DDEBUG=DBGLVL_TEST -Isrc -o example example.c
```

Compile with diagnostics disabled:

```sh
cc -DNDEBUG -Isrc -o example example.c
```

In the debug build, `dbg` emits structured diagnostics to `stderr`. In the release build, message and check macros compile to no-ops. Block macros are described separately below because their marker code may disappear while their enclosed C block still exists.

## Include And Build Model

`dbg` is header-only:

```c
#include "dbg.h"
```

Recommended compile flags for common modes:

```sh
# Error-level diagnostics only
cc -DDEBUG=DBGLVL_ERROR -Isrc -o app app.c

# Warnings and errors
cc -DDEBUG=DBGLVL_WARN -Isrc -o app app.c

# Informational diagnostics too
cc -DDEBUG=DBGLVL_INFO -Isrc -o app app.c

# Test, trace, and timing macros
cc -DDEBUG=DBGLVL_TEST -Isrc -o app app.c

# Allocation/memory tracing without test-level features
cc -DDEBUG_ALLOC -Isrc -o app app.c

# Test-level features plus allocation/memory tracing
cc -DDEBUG=DBGLVL_TEST -DDEBUG_ALLOC -Isrc -o app app.c

# Release-style build: force all debug switches off
cc -DNDEBUG -Isrc -o app app.c
```

`NDEBUG` has priority over both `DEBUG` and `DEBUG_ALLOC`. If `NDEBUG` is defined, `dbg.h` undefines both switches.

## Debug Levels

`DEBUG` controls the ordinary diagnostic and test macros.

| Level | Value | Enabled Macros |
|---|---:|---|
| `DBGLVL_ERROR` | `0` | `dbgerr` |
| `DBGLVL_WARN` | `1` | Error-level macros plus `dbgwrn` |
| `DBGLVL_INFO` | `2` | Warning-level macros plus `dbginf` |
| `DBGLVL_TEST` | `3` | Info-level macros plus `dbgvrb`, test, block, and clock macros |

When `DEBUG` is not defined, the public macros still exist. Message and check macros discard their arguments. Block-style macros need more care: marker macros such as `dbgclk`, `dbgvrb`, and `dbgtst` may leave the enclosed C block in place, while `dbgblk` is specifically for code that should not run unless test-level debugging is enabled.

`DEBUG_ALLOC` is independent from the level ladder. It enables allocation and memory-operation wrappers. If `DEBUG_ALLOC` is defined while `DEBUG` is not, `dbg.h` defines `DEBUG` as `DBGLVL_ERROR` internally so the allocation wrappers can use the shared diagnostic machinery.

## Message Macros

### `dbgerr(...)`

Use `dbgerr` for error diagnostics. It adds the library error prefix and a source file/line suffix.

```c
if (!fp) {
  dbgerr("could not open %s", path);
}
```

Current output begins with `ERROR:` and includes the source location.

### `dbgwrn(...)`

Use `dbgwrn` for warnings that should appear only at `DBGLVL_WARN` and above.

```c
if (cache_entries > cache_limit) {
  dbgwrn("cache over limit: %d > %d", cache_entries, cache_limit);
}
```

### `dbginf(...)`

Use `dbginf` for normal progress or state diagnostics. It appears only at `DBGLVL_INFO` and above.

```c
dbginf("loaded %zu records", record_count);
```

### `dbg_msg(...)` And `dbg_prt(...)`

`dbg_msg` and `dbg_prt` are internal message primitives used by the public macros. Do not call them from application code. Prefer `dbgerr`, `dbgwrn`, `dbginf`, or a higher-level block macro.

## Marking Program Output With `dbgvrb`

Use `dbgvrb(...) { ... }` at `DBGLVL_TEST` when code intentionally writes to `stderr` and you want report tooling to distinguish that program output from diagnostics generated by `dbg` itself.

```c
dbgvrb("parser stderr output") {
  fprintf(stderr, "input line: %s\n", line);
  fprintf(stderr, "token count: %d\n", count);
}
```

At `DBGLVL_TEST`, this emits `VERB [ ...` before the block and `VERB ]` after it. Below `DBGLVL_TEST`, the enclosed block still executes, but the verbose markers disappear. The enclosed output is ordinary program output; the markers merely classify it for later log processing.

Use `dbgvrb` when:

- The program under test legitimately writes to `stderr`.
- You are testing an error path that prints diagnostics.
- You want external log formatting/reporting to preserve and label that output rather than treat it as a `dbg` diagnostic.

Do not use `dbgvrb` as a replacement for `dbginf` or `dbgwrn`. It is an output-classification block, not a diagnostic severity level.

## Testing Macros

Testing macros are enabled at `DEBUG >= DBGLVL_TEST`.

### `dbgtst(...) { ... }`

Use `dbgtst` to mark a named test block.

```c
dbgtst("vector push/pop") {
  vec_t v = vec_new();
  vec_push(&v, 42);
  dbgchk(vec_pop(&v) == 42, "");
}
```

At test level, the block emits `TEST [ ...` before the body and `TEST ]` after the body. Future reporting tools can use these markers to group checks.

`dbgtst` does not generate a `main` function, count totals, or return a test result by itself. The current design keeps `dbg.h` lightweight; richer reporting belongs in external tooling.

`dbgtst` blocks cannot be nested. Start each test case at top level instead of placing one `dbgtst` inside another.

When test-level debugging is disabled, the test markers and checks are compiled out, but any ordinary C statements inside the braces may still execute. Keep test-only code in test-only source files, or put side-effecting debug-only statements inside `dbgblk` when they must not run outside test builds.

### `dbgchk(expr, message, ...)`

Use `dbgchk` for lightweight checks. A message is recommended when a failure needs context. The short form without a message works on common compilers used by the test suite, but relies on an empty `__VA_ARGS__` extension; pass an empty string when you want strictly portable C99 source.

```c
dbgchk(ptr != NULL);
dbgchk(count == expected, "");
dbgchk(buffer[0] == '\0', "");
```

`dbgchk` does not set `errno`. If you need to react programmatically to a check failure, use `dbgmst` to abort or a regular `if` statement outside the debug macros.

Use a formatted message when a failure needs context.

```c
dbgchk(user_id > 0, "invalid user id: %d", user_id);
dbgchk(nread == expected, "read %zu bytes, expected %zu", nread, expected);
```

The formatted message is printed only when the expression fails. Passing checks do not print the message.

Prefer short failure messages that state the useful runtime values. The expression itself is already printed by `dbgchk`.

### `dbgmst(expr, message, ...)`

Use `dbgmst` for must-pass preconditions. It behaves like `dbgchk`, then aborts if the check failed.

```c
FILE *fp = fopen(path, "rb");
dbgmst(fp != NULL, "required file is missing: %s", path);
```

When no extra failure message is needed, pass an empty string:

```c
dbgmst(config != NULL, "");
```

Use `dbgmst` sparingly. It is best for prerequisites that make the rest of the test invalid or unsafe.

### `dbgblk { ... }`

Use `dbgblk` for setup, inspection, or diagnostic code that should run only at test level.

```c
dbgblk {
  dump_tree(root);
}
```

This is useful when a block is too large or too imperative to fit naturally inside a single message macro. Unlike clock, verbose, and test marker blocks, `dbgblk` is the block form to use when the enclosed code itself must disappear from non-test builds.

### `dbgtrk(...) { ... }`

Use `dbgtrk` for trace-based testing: declare which strings you expect to appear (or not appear) in the log output of a block.

```c
dbgtst("allocation pattern") {
  dbgtrk("=alloc(16)", "!alloc(0)") {
    void *p = malloc(16);
    dbginf("alloc(%zu)", 16);
    free(p);
  }
}
```

Each expectation is a string with a prefix:

- `=string` — the string must appear somewhere in the block's log output.
- `!string` — the string must **not** appear.

Expectations without a prefix are not valid. You may mix `=` and `!` expectations in a single `dbgtrk` call.

`dbgtrk` behaves differently from other test macros: the block itself does not perform pass/fail checks at runtime. Instead it emits `TRACK[` before the block and `TRACK]` after it. The `dbglog` post-processing tool reads the raw log and compares the captured lines between those markers against the declared expectations, injecting `PASS :` or `FAIL :` lines.

```text
TRACK[ "=alloc(16)", "!alloc(0)" t_trk.c:22
INFO : alloc(16) t_trk.c:22
TRACK]
PASS : (=alloc(16)) t_trk.c:20
PASS : (!alloc(0)) t_trk.c:20
```

A `dbgtrk` block can hold up to 8 expectations. Additional expectations are silently ignored. Expectation strings that exceed the internal buffer are truncated and will never match.

`dbgtrk` blocks cannot be nested. Start each trace block at top level inside a `dbgtst` or other enclosing scope.

## Timing With `dbgclk`

Use `dbgclk(...) { ... }` to measure CPU time spent in a block.

```c
dbgclk("sort %zu items", nitems) {
  qsort(items, nitems, sizeof(items[0]), compare_items);
}
```

The macro prints a `CLOCK[` start marker with a millisecond timestamp and description, runs the block, then prints a `CLOCK]` elapsed-time line. It uses `clock_gettime(CLOCK_MONOTONIC)`, measuring monotonic elapsed time in milliseconds. On Arduino it uses `millis()` instead.

When timing is disabled, the timing output is omitted but the enclosed code still runs.

Good uses:

- Quick comparisons during development.
- Detecting obvious performance regressions.
- Marking expensive blocks in debug logs.

Poor uses:

- Precise benchmarking.
- Measuring sleep, I/O wait, or wall-clock latency.
- Making pass/fail decisions from tiny timing differences.

## Grouping Debug Code

`DBG_ON` and `DBG_OFF` let you define project-specific switches for related debug calls.

```c
#define DBG_PARSE DBG_ON
#define DBG_CACHE DBG_OFF

DBG_PARSE(dbginf("token: %s", token));
DBG_PARSE(dbgchk(token != NULL, ""));

DBG_CACHE(dbginf("cache hit: %s", key));
```

Change a group to `DBG_OFF` when you want to keep the instrumentation in place but compile it out:

```c
#define DBG_PARSE DBG_OFF
```

This is useful for focused debugging campaigns. You can leave well-named debug groups near the code they explain without cluttering future logs.

## Temporarily Disabling Individual Calls

Most public macros have underscore-prefixed no-op counterparts:

```c
_dbginf("temporarily quiet");
_dbgchk(expensive_check(), "skip this check for now");
```

Available disabled forms:

- `_dbgtst`
- `_dbginf`
- `_dbgvrb`
- `_dbgwrn`
- `_dbgerr`
- `_dbgchk`
- `_dbgmst`
- `_dbgptr`
- `_dbgclk`
- `_dbgblk`

Use these sparingly. Prefer grouping with `DBG_ON` and `DBG_OFF` when multiple related diagnostics should be toggled together.

## Allocation And Memory Tracing

Define `DEBUG_ALLOC` to wrap common allocation and memory functions.

```sh
cc -DDEBUG_ALLOC -Isrc -o app app.c
```

With `DEBUG_ALLOC`, calls to these functions are redefined through `dbg` wrappers:

- `malloc`
- `calloc`
- `realloc`
- `free`
- `strdup`
- `strndup`
- `strcpy`
- `strncpy`
- `strcat`
- `strncat`
- `memcpy`
- `memmove`
- `memset`

Allocation wrappers emit `M:` lines. Memory/string operation and pointer-check wrappers emit `M?` lines.

Example:

```c
#include <stdlib.h>
#include "dbg.h"

int main(void) {
  char *p = malloc(16);
  dbgptr(p);
  free(p);
  return 0;
}
```

Compile with:

```sh
cc -DDEBUG_ALLOC -Isrc -o alloc alloc.c
```

`dbgptr(p)` emits a pointer check line. It is available only when allocation tracing is enabled.

Important cautions:

- `DEBUG_ALLOC` redefines standard and POSIX function names with macros. Enable it deliberately and locally.
- Include order matters. Since the wrappers are macros, they affect code after `dbg.h` is included.
- `strdup` and `strndup` are POSIX-style functions. Portability depends on the compiler and C library.
- Use `NDEBUG` to suppress allocation tracing in release builds.

## Log Formatting With `dbglog`

`dbglog` is the external log-formatting tool in `src/dbglog.c`. It reads `dbg` output and formats it either as readable plain text or as a single static HTML report.

Build it with:

```sh
make -C src
```

Options:

```text
-h  show help and usage
-H  render HTML instead of plain text
-F  show only failures
-v  show version
```

With no file arguments, `dbglog` reads from standard input.

### Plain Text Mode

The default mode produces a human-readable report. Event codes are expanded to uniform-width markers (`ERROR:`, `WARN :`, `INFO :`, `TEST [`, `PASS :`, `FAIL :`, `MEM  :`, etc.). Source file and line are appended directly after each event.

```sh
./src/dbglog test/test.log
./program 2>&1 | ./src/dbglog
```

Example output:

```text
ERROR: something went wrong test.c:42
TEST [ test case 1 test.c:50
PASS : x == 1 test.c:51
FAIL : y == 2 test.c:52
FAIL = failure detail here
TEST ]
```

### Failure-Only Mode (`-F`)

Shows only failures: `ERROR:` lines, `FAIL :` checks, `FAIL =` detail lines, and `FAIL` memory-check results. PASS lines, info, warnings, verbatim output, and clock markers are suppressed.

```sh
./src/dbglog -F test/test.log
```

### HTML Mode (`-H`)

Renders a single static HTML page with color-coded lines:

- Green — passing checks and memory validations
- Red — failures and errors
- Yellow — warnings
- Blue — informational diagnostics
- Purple — test and track blocks
- Light blue — clock and memory allocation events
- Green-tinted — verbatim program output

```sh
./src/dbglog -H test/test.log > report.html
```

### Memory Validation

When allocation tracing is enabled (`DEBUG_ALLOC`), `dbglog` tracks every `M:` allocation event (malloc, calloc, realloc, free, strdup, strndup) and validates every `M?` boundary-check event against the known allocation table. Each `M?` line is followed by a `PASS` or `FAIL` result with the available buffer size.

```text
MEM  : malloc 32 A1B2C3D4 test.c:10
MEM  ? strcpy A1B2C3D4 ... 5 test.c:11
PASS strcpy 0xA1B2C3D4 +5 (buf=32) test.c:11
MEM  : free A1B2C3D4 test.c:13
MEM  ? pointer A1B2C3D4 test.c:14
FAIL pointer 0xA1B2C3D4 test.c:14
```

Violations detected include use-after-free, buffer overflow, out-of-bounds pointers, and non-heap addresses.

### Track Validation

`dbglog` evaluates `dbgtrk` expectations. It parses the `=` and `!` strings from the `TRACK[` marker, scans all log lines between `TRACK[` and `TRACK]`, and reports `PASS :` or `FAIL :` for each expectation. The source location is taken from the enclosing `TEST [` block.

```text
TEST [ allocation pattern test.c:20
TRACK[ "=alloc(16)", "!alloc(0)" test.c:21
INFO : alloc(16) test.c:22
TRACK]
PASS : (=alloc(16)) test.c:20
PASS : (!alloc(0)) test.c:20
TEST ]
```

## Release Builds And Source Hygiene

The intended workflow is to leave diagnostic calls in source code and use compile flags to control their output.

```c
int parse_record(const char *line) {
  dbginf("parsing: %s", line);

  if (!line) {
    dbgerr("null input line");
    return -1;
  }

  dbgchk(line[0] != '#', "comment unexpectedly reached parser");
  return 0;
}
```

In a build without `DEBUG`, the message and check macros compile without emitting diagnostics. This keeps instrumentation close to the code it explains.

Be deliberate with block macros in production code. If a block contains normal program behavior, `dbgclk` or `dbgvrb` are appropriate because the behavior should still run when markers are disabled. If a block contains debug-only behavior, use `dbgblk` or an explicit preprocessor guard.

## Getting The Most From dbg

Use the lowest useful debug level:

- Use `DBGLVL_ERROR` for serious diagnostics that should be visible in most debug builds.
- Use `DBGLVL_WARN` for suspicious but recoverable states.
- Use `DBGLVL_INFO` for ordinary progress logs.
- Use `DBGLVL_TEST` for tests and timing.

Write checks that explain intent:

```c
dbgchk(header.magic == EXPECTED_MAGIC,
       "magic mismatch: got 0x%08X", header.magic);
```

Use `dbgvrb` to protect real program output in logs:

```c
dbgvrb("compiler stderr") {
  run_compiler_that_writes_to_stderr();
}
```

Use groups to avoid deleting useful diagnostics:

```c
#define DBG_IO DBG_ON

DBG_IO(dbginf("open %s", path));
DBG_IO(dbgchk(fd >= 0, "open failed for %s", path));
```

Do not accumulate pass/fail state in application code. `dbg.h` leaves counting and reporting to external log processing. Use `dbglog` or your own tooling rather than adding counters to production code.

## Complete Example

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include "dbg.h"

#define DBG_PARSE DBG_ON

static int parse_number(const char *s, int *out) {
  DBG_PARSE(dbginf("parse_number input=%s", s ? s : "(null)"));

  if (!s || !out) {
    dbgerr("invalid parse arguments");
    return -1;
  }

  char *end = NULL;
  long value = strtol(s, &end, 10);

  if (*end != '\0') {
    dbgwrn("trailing characters in number: %s", end);
    return -1;
  }

  *out = (int)value;
  return 0;
}

int main(void) {
  dbgtst("parse valid number") {
    int value = 0;
    dbgchk(parse_number("42", &value) == 0);
    dbgchk(value == 42, "value=%d", value);
  }

  dbgtst("parse invalid number") {
    int value = 0;
    dbgchk(parse_number("42x", &value) != 0);
  }

  dbgclk("program stderr demonstration") {
    dbgvrb("intentional stderr") {
      fprintf(stderr, "this belongs to the program, not dbg\n");
    }
  }

  return 0;
}
```

Compile for full test-level output:

```sh
cc -DDEBUG=DBGLVL_TEST -Isrc -o parse_test parse_test.c
```

Compile with allocation tracing too:

```sh
cc -DDEBUG=DBGLVL_TEST -DDEBUG_ALLOC -Isrc -o parse_test parse_test.c
```

Compile for release:

```sh
cc -DNDEBUG -Isrc -o parse_test parse_test.c
```

In that release build, `dbg` markers and checks are suppressed. Ordinary program code inside marker blocks still follows normal C execution rules, so keep test-only source separate from production entry points when necessary.

## Limitations

These limitations are deliberate tradeoffs in how `dbg.h` works:

- `dbg.h` does not accumulate pass/fail totals or generate a `main` function. Rich reports are expected to come from external tooling.
- `DEBUG_ALLOC` wraps calls via function-like macros. Calls through function pointers, such as `void (*f)(void*) = free; f(p);`, bypass logging and can make `dbglog`'s allocation model drift from reality.
- Redefining libc names such as `malloc` and `memcpy` as macros is formally outside the C standard, and it also instruments inline functions in any header included after `dbg.h`. Prefer including `dbg.h` last.
- `break`, `goto`, or `return` inside `dbgtst`, `dbgtrk`, `dbgvrb`, or `dbgclk` skips the closing marker and leaves an unbalanced log. `continue` closes the block early. These macros are based on `for` loops.
- Dangling `else` can bind to the macro's internal `if`: write `if (c) { dbgtst(...) { ... } } else { ... }`, not `if (c) dbgtst(...) { ... } else { ... }`.
- Emission is not thread-safe. One event is written with several stdio calls, so concurrent threads can interleave mid-event.
- A newline or `\x0F` byte inside a user message breaks the one-line-per-event framing that `dbglog` relies on.
- `dbgchk(expr)` without a message relies on empty `__VA_ARGS__`, a pre-C23 extension accepted by common compilers such as gcc, clang, and MSVC. For stricter C99 source, write `dbgchk(expr, "")`.
- Nested `dbgtst` and `dbgtrk` blocks are rejected at compile time by design. The diagnostic points at a line whose comment explains the restriction. Cross-function nesting, where a called function starts another block, is not detected.

These limitations help keep `dbg` small enough to include directly in C projects while leaving report generation and log analysis to external tooling.
